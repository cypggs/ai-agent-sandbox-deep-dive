01

一句话看懂

先建立直觉，再谈细节。

Fact2026 年 9 月，Meta 发布 Muse：一个有名字、有记忆、替你办事、App 关了还在跑的个人智能体。三周内 OpenAI、Manus 相继跟进。nanoMuse 是浙大团队在 9 月 25 日开源的完整对位产品——不是论文 demo，10 月 9 日已发 1.0，手机/桌面/Web 三端可装。

Analysis理解 nanoMuse 的总钥匙是 shape（形态），不是模型。Muse 把"每人一台云 VM"卖给你；nanoMuse 说：agent 应该跑在你已经拥有的硬件上，多台设备之间用一个你自己能搭的中继连成同一段对话。论文原话："Who runs that program, where, and under whose eyes is not a detail of deployment. It is the product."（谁运行这个程序、在哪里、在谁的眼皮底下，不是部署细节，它就是产品本身。）

图 1 · 形态对比。左边是"云里的一台电脑"，右边是"你手里的每台设备"。理解了这张图，就理解了论文 12 页里一半的论证。
一句话记住它：nanoMuse = 设备端 agent（OpenMinis 魔改手机端 + DeepSeek Harness 桌面端）+ Hands 读屏操作 + Sentinel 安全门 + 可自建中继，全部 GPL 开源。论文里那句"an open counterpart had to exist"（开源对位必须存在）就是它的立项理由。

03

架构深读：shape 才是本质差异

把"每台设备一个完整 agent"这句话拆开，看它到底是怎么连起来的。

🧩 四端各自为战，中继只当"接线员" Fact

每台设备都跑完整的一套：agent 主循环 + 自己的 Sentinel + 记忆。设备之间是 peer（对等） 关系——手机的 agent 可以把"去 Mac 上把订单号填进表格"这个任务派给 Mac 的 agent，被派活的设备先自己同意（走它自己的 Sentinel），权限不跨设备借用。

中继（nanoMuse Cloud）是唯一共享的部件，但被刻意做小：单进程 + 一个 SQLite 文件，idle 仅 85MB。它只存 5 样东西——账号（哈希 ID）、token/费用账本、agent 画像、设备在线状态、用户选择同步的对话文本；永远不碰文件、截图和 tool 返回内容。社区中继给免费模型额度，用完换自己的 key；一台最小 VPS（¥30–60/月）就能自建。

图 2 · nanoMuse 运行架构。设备是完整的 agent 而非瘦客户端；中继是可选的"接线员"，不是大脑。类比：Muse 像"一个大脑+多个显示器"，nanoMuse 像"几个各有大脑的同事+一个群聊"。
Analysis这个 shape 是一次诚实的 trade-off。Muse 用"每人一 VM"换来真隔离（seccomp + 内核级 taint 追踪），代价是订阅制、美国独占、闭源；nanoMuse 用"设备端 agent"换来可自托管和屏幕操作能力（云 VM 永远摸不到你手机里的银行 App），代价是安全边界从特权边界退化为同进程策略边界（详见 §11）。没有银弹，只有取舍——论文把这笔账算得很清楚。
04

Hands：爬梯子，最后一 rung 才是读屏

这是 nanoMuse 相对所有云 VM 路线最硬的差异化：云里的 agent 永远摸不到你手机上的银行 App。

🪜 先爬梯子，够不着才用手 Fact

设计哲学叫 ladder（梯子）：skill → 命令行工具 / MCP → 带用户登录态的页面抓取 → 浏览器 → 最后才是屏幕。Hands 默认关闭，是"实在没别的办法"时的最后一招——这与"把读屏当默认操作方式"的粗暴路线划清了界限。

最低的能用的 rung ① skill / MCP / 命令行 —— 有现成工具就用工具 ② 带登录态的页面抓取 —— 复用你的登录 ③ 浏览器 —— 能当网页办就当网页办 ④ Hands 读屏 —— 默认关闭，最后一招 一次一截屏 · 一次一动作 · 每步都要"说话" 便宜 ↕ 贵/慢/险 ✅ 可靠、可审计 ✅ 复用登录态 ✅ 通用 ⚠️ 看图说话，易错 手机端 operator 移植自 MemGUI-Bench（MIT），桌面端移植自字节 UI-TARS-desktop；坐标系 999×999（Qwen-VL 方言） iOS 无 Hands（系统不允许）；Linux Hands 仅 X11
图 3 · Hands 的"梯子"。读屏是成本最高、最不可靠的一 rung，所以被放在最后且默认关闭——这是工程成熟度的体现，不是功能缺失。

🗣️ 治理靠"说话"，不靠"看图" Fact Analysis

这是全项目我最欣赏的一个降维设计：确定性策略判断不了一张图片，但能判断模型自己写的那句话。所以 Hands 循环强制模型每步输出三样东西：thought（思考）+ 一句话人话（"我将要做什么"，用户看得懂）+ 一个手势（点/滑/输）。Sentinel 审查的是那句人话：

模型说的话里出现…判定
"确认支付 / 转账 / 提交订单 / 发送 / 删除"整步变 sensitive，每次都要你点头
打字 + 回车一次完成（messenger 里回车 = 发送）sensitive——"一次输完就发出"太像手滑
tap 但没有 label（不知道点的是什么）warning——"盲点"本身就可疑

Android 上还会读无障碍树里手指落点的文本，取"模型说的话"和"落点文本"中更严格者。operator 的 prompt 里明文禁止输入密码、PIN、卡号、验证码——登录/支付这种事，Hands 只负责把你带到输入框，手交给你，点 Done 继续。

Analysis产品细节同样用心：手机操作时 App 上方悬浮胶囊（头像+当前步骤+红色 Stop），落点画圈；电脑端屏幕边缘呼吸光+落点标记；操作过程不录屏，而是存成 trajectory（每步截图+动作画线）进聊天记录。论文原话："我们做了 Muse 式的 dimmed live stage 然后扔掉了——trajectory 可回看，动图不行。"对"事后可审计"而言，这是对的。

05

Sentinel：最值得抄走的设计

如果只从这个项目带走一样东西，带走 Sentinel。不是代码（GPL），是它的决策思想。

🚦 六步决策序：每个 tool call 的必经之路 Fact

agent 永远不直接执行工具，一律走 Sentinel.guard()。六步中第一步命中的说了算：

图 4 · Sentinel 六步决策。⑤⑥ 是"安全带"：它们只能收紧、不能放松——这是整个设计里最关键的一行。

🎫 审批是 capability，不是心情 Analysis

每个授权绑定 grant key = 工具 + 触达目标：web_fetch:example.com、send_email:alice@x.com、shell:git。批了 git 不代表批了 curl；git status | head 要逐个程序授权。时效分六档：拒绝 / 仅此一次 / 本次对话 / 到重启 / 24小时 / 永久（永久可随时撤销）。带 warning 的调用永远只能"一次"——付款、密码没有"总是允许"，用户说 always 也不行。

📦 沙盒 + 凭据：纵深的两道墙 Fact

bubblewrap 沙盒（Linux）：每个 shell/python 调用独立 namespace——workspace 是唯一可写区，/usr /etc 只读，home 目录不存在（vault、ssh key、云凭证全看不见），无网络除非调用被判定需要（network=true 即走 egress 审批）。环境变量大扫除：*KEY* *TOKEN* *SECRET* AWS_* GH_* 等全部剥离——模型写的代码读不到模型自己的 key。

Vault：Fernet 加密，模型只见 {{vault:NAME}} 占位符；shell 里敢带占位符直接拒绝执行；任何 tool 输出里出现 secret 先 redact 再给模型看。

诚实声明Sentinel 是"策略边界"，不是"特权边界"。论文原话："A policy boundary is not a privilege boundary."——它和 agent 跑在同一个进程、同一个信任域里。规则能拦住被说服的模型，但设备被攻破 = agent 被攻破，不像 Muse 那样有个"够不着"的外部 Sentinel。这是架构级差距，文档把这句话放在了最显眼的位置。

记忆：双轨制与诚实的短板

"记忆是可改的 Markdown 文件"——这句话只说对了一半，另一半藏着 trade-off。

图 5 · 记忆双轨。"可读可改"和"可召回可撤销"各走一条路——手机要的是透明，桌面要的是能力。

📝 自曝的短板：记忆没有"出身证明" Fact

论文 §7 原话大意：弱模型随手写的一行，会被下周的强模型当事实来读——store 只记了"什么时候改的"和"能撤销"，没记"哪个模型写的、可信度几分"，也没有"旧行重检"的规则。"在补上之前，记忆页应被当作一位还不完全信任的同事的笔记来读。"

roadmap 里排了修复项：provenance on every line（每行标注模型+日期+置信度）+ 重检规则。这恰恰是 openmuse 长期记忆 v1.1 可以提前加上的——比事后做 explain 更根本。

07

论文的隐藏价值：一份 Muse 逆向阅读报告

论文第 3 章不写 nanoMuse，写的是" Muse 是怎么造的"——这是公开资料里对 Muse 架构最细的第三方拆解，本身就值得一读。

🔍 四档来源标注：学术诚信的范本 Fact

作者基于四份 Meta 公开文档（发布公告、安全架构长文、设计长文、隐私帮助页）+ 一份 Muse 生产版 system prompt 拷贝 + 已发布客户端实测，还原了 Muse 的系统图（论文 Figure 3）。每一句话都标注来源档：

标注含义例子
documentedMeta 公开说过的每人一台 Linux VM、Sentinel 是"唯一授权方"
prompt那份 prompt 拷贝里读到的部署约每小时替换 VM、home 目录持久化
observed已发布客户端里看到的工具调用 chip、Feed/想法/目标五个房间
inferred作者的推断"这就是操作系统在沙盒渲染器和特权 broker 之间的经典拆分"

作者还主动声明：prompt 拷贝的来源无法验证（只验证了它与另两份文档自洽），prompt 随部署一直在变，"10 月读到的可能不是你读这篇论文时跑的版本"——标了 prompt/inferred 的结论要打折听，Meta 出新资料他们会更正。

🏆 为什么 Muse 赢

Analysis论文的判断：Muse 不是赢在 benchmark，而是赢在 shape——"十个在一屏手机上看得见的决定"：一个有名字的 agent、一段长对话、工具 chip、审批卡片、可编辑的记忆文件……把后台 agent 做"可读"（legible），人才敢让它一直跑着。设计预算花在了 legibility 上。

🛡️ 安全架构的精髓

论文提炼：概率层（模型训练+分类器 ensemble）减少被说服的次数；确定性层（边界）限定被说服后能造成的伤害——"即使 Muse 被说服去做坏事，边界依然成立"。浏览器子 agent 只看无障碍树快照而非 DOM，是"用能力换安全"的刻意 trade-off。

📉 能抄走 vs 抄不走

论文结论：能转移的是"把所有安全机制放在 agent 够不着的地方"这条原则 + 花在 legibility 上的设计；转移不了的是每人一 VM 的成本结构和自研模型。这正是 nanoMuse 只抄前者、用"设备端+策略边界"替代后者的原因。

08

五问三环：个人智能体"应该"是什么样子

论文第 4 章是纯观点，作者明说"要超越今年秋天的一切，包括我们自己的"。这是全篇思想密度最高的一节。

图 6 · 五问三环（仿论文 Figure 4）。五个问题是扇区，三层时间是同心环：内环是 2026 已有，中环是开源接着做的事，外环是"能用很多年"的 agent。

🧠 它知道什么——记忆要能"带走"

一个记你很多年的 agent，会持有世上最完整的关于你的记录。它应该是 plain files、你的语言，你能打开、改、删、导出给别的 agent——这是 agent 能活得比模型和设备更久的前提。还要有 provenance（哪行哪个模型何时写的、可信度几分）和重检规则：人写的一行，永远压过模型写的一行。

✋ 它在哪动手——"一只 agent，很多手"

人不该有"每个 App 一个 agent"，而该有一个常任代表。凡是有屏/麦克风/马达的东西，都是它的一双手。2026 年的手是云电脑+浏览器+语音；nanoMuse 加上了手机自己的屏幕；再往后是机器人和家电——"不共享主人 agent 的机器人，只是家电"。

🤝 它向谁负责——审批是"信任的语法"

发送、付款、删除、签署——不可撤销的事，授权与收回就是人和 agent 谈论信任的语言。应该是一套小而规律的语言：一次/本次对话/永久+可撤销，在哪台设备上都能问，批的东西原样展示。有些授权不该存在：付款和密码，永远不设"记住"，用户说多少次 always 都不行。

🌱 它怎么学 & 谁出钱——把账算清

agent 和助手的区别是 agent 会先开口——这也是它最容易失去你的地方。打扰的门槛必须看得见、搬得动。而"谁出钱"决定"听谁的"：一台 VM 一人的 agent 只能靠订阅或大厂别的生意养；开源对位应该让人直接向 provider 付费，或花一台小鸡的钱自建中继。远期是 commons（公地）：技能、评测、开放模型由数据的主人共治。

成本与体量：小到能装进口袋

"nano"的含义：整套东西小到你自己跑得起、部署得起。论文 Table 2 原样转述。

10

对 openmuse 的启示：红线与可借鉴清单

本馆馆长自己的项目 openmuse（MIT）与 nanoMuse 路线互补，这一节是"能拿走什么、不能碰什么"的清单。

红线GPL-3.0-or-later 有传染性：nanoMuse 的代码不能直接搬进 MIT 协议的 openmuse，否则整个项目会被迫转 GPL。可以借鉴的是思想、协议设计、决策流程（idea 不受版权保护），不要复制代码段。论文本身按 arXiv 惯例是 CC BY，引用观点没问题。

✅ 可借鉴的思想（按价值排序） Analysis

  1. Sentinel 六步决策序——deny → 用户规则 → allow/ask 名单 → risk×mode → taint → warnings。openmuse 的工具审批若还没成体系，这套可直接当设计蓝本；第 5 步 taint 规则（"读过私密数据后对外 egress 一律 ask，auto 也不豁免"）是对抗 prompt injection 外带数据最便宜的确定性防线。
  2. Approval as capability——grant key 绑定"工具+目标"、六档时效、warning call 永不"always"。比二元"允许一次/始终允许"细腻一个量级。
  3. Hands 的"语言治理"——让模型用一句话说出将要做什么，用确定性策略审查这句话。openmuse 若做 device 端操作，这是"屏幕操作可治理化"的现成思路。
  4. bubblewrap 沙盒设计——workspace 唯一可写、home 不可见、按需给网、环境变量 scrub。openmuse 的 E2B 侧已有 VM 隔离，device 侧执行缺的正是这一块。
  5. Trajectory 存档而非直播——操作过程存为可回看的步骤序列，比实时录屏更利于事后审计，也更便宜。
  6. 记忆 provenance——每行记"哪个模型、何时、几分可信"，openmuse 长期记忆 v1.1 可提前加上，比事后 explain 更根本。

🔀 路线互补，不是替代

openmuse = per-user 云 sandbox（E2B）+ 强隔离；nanoMuse = 设备端 agent + 可选 relay + 屏幕操作。前者在隔离性上更强，后者补的是"够到用户真实设备"这一块。若 openmuse 未来做 companion device / 本地执行，nanoMuse 的 hub 帧协议和 Sentinel 是现成的思想库。

🔭 值得跟进的 roadmap

Hands 评估套件（AndroidWorld / OSWorld / MemGUI-Bench / OS-Harm 并跑，每版本出分）——这个思路可直接抄：给 computer-use 建回归基准。自研 open hands model（用户自愿贡献的 traces 训练）——"最敏感的环路不依赖 vendor 模型"，长期方向与 Anthropic Mods、Google Agent Sandbox 的思路同频。

11

短板与风险：论文自己承认的七件事

第 7 章是全篇最诚实的一章，转述如下——一个敢把"不覆盖清单"写进论文的项目，可信度本身就加分。

1️⃣ 策略边界 ≠ 特权边界

Sentinel 与 agent 同进程同信任域。规则能拦住被说服的模型，但设备被攻破 = agent 被攻破。这是架构级差距，不是调参能补的。

2️⃣ Hands 没有测量数据

原话："我们没有成功率，也没有人工接管次数——这个数字还不存在，我们宁愿承认也不编一个。"生产环境用 Hands 做关键操作目前是盲飞。

3️⃣ 中继存文本

同步的对话文本存在中继服务器上；社区中继是项目方一台机器上的单进程。自建可解，但默认是信任项目方。

4️⃣ "帮助改进模型"默认开启

opt-out 开关，论文自认"这是本项目最没把握的一个选择"——用默认换开源模型，对隐私最不友好。

5️⃣ 平台限制

iOS 无 Hands（系统不允许）；Linux Hands 仅 X11，Wayland 不行；macOS/Windows 上 bubblewrap 沙盒不工作，shell 直接以用户身份跑。

6️⃣ 默认不安全项

API 默认 HTTP 明文 + Bearer token（文档自己喊"别暴露到公网"）；vault.key 默认躺在 data dir 旁边，能读目录就能解密；DNS rebinding 未完全防住。

7️⃣ Approval fatigue

文档原话："如果卡片不看就点通过，以上全白费。"再好的 Sentinel 也救不了全点"允许"的用户。
