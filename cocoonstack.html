CocoonStack 全栈深度解读
不用 etcd 存沙盒的 microVM 舰队

2026 年下半年，一套名叫 CocoonStack 的开源全栈悄悄长成：底层是把 Cloud Hypervisor 包装成 Docker 式 CLI 的 microVM 引擎 cocoon，中层是每节点一个守护进程的热池 sandboxd，顶层是一个在 etcd 里一个沙盒对象都不存的聚合式 Kubernetes APIServer。它宣称一次 kubectl patch 就能在 20 台裸金属上 15 秒拉起 50,000 台 microVM，而 etcd 全程只有约 2 次写/秒。本报告把三仓代码与全部官方文档逐页读完后写成：分层对齐、数字溯源、协议边界与风险一并交代。

01

一句话看懂

先建立直觉，再逐层拆开。

FactModal 曾发文论证「Kubernetes 到不了 100 万并发沙盒」：调度是 O(n×p) 且串行、每个 Pod 触发多次 etcd 写入、etcd 在单个 keyspace 内不可分片。它的解法是离开 Kubernetes，自建无状态调度器 + Redis 流。CocoonStack 的 scaling-design.md 直接回应：诊断是对的，但要拿掉的是集中式事务路径，不是 K8s 的 API 语义——K8s 自己就有先例：kubelet 静态 Pod（节点先干、apiserver 后记）、Lease（心跳专用小对象）、metrics.k8s.io 聚合层（scatter-gather 实时节点状态、etcd 零存储）。

Analysis整套栈的赌注一句话：把 Kubernetes 降级为「意图记录 + 策略面」，把事务面下沉到节点本地。etcd 只存「想要多少」（一个 WarmPool 对象）和「每节点有什么」（一个 NodeInventory 对象），单个沙盒的存在与否只活在节点内存与本地文件里。于是对象数从 O(sandboxes) 降到 O(pools + nodes)，扩容速度只取决于节点本地能多快克隆快照——而那是引擎层 cocoon 用 mmap 写时复制解决的问题。

一句话记住它：CocoonStack = cocoon（microVM 引擎，快照克隆原语）+ sandboxd（节点热池，亚毫秒 claim）+ sandbox-apiserver（聚合层，etcd 零沙盒对象），再套一个 e2b 兼容面，让未修改的 e2b SDK 改个 E2B_API_URL 就能从这套自托管舰队里领沙盒。

03

全栈架构：L0–L3 四层对齐

官方 scaling-design 把自己拆成四层 staging。注意诚实标注：L1 已交还上游、L2 只设计未实现、真正属于本栈自研的是 L0 与 L3。

图 1 · CocoonStack 分层。L3 读路径靠 NodeInventory 扇出合成，写路径（claim）直达节点；etcd 对象数 O(pools + nodes)，与沙盒数无关。

L0 · API 卫生

前置条件：周期读全走节点级 informer cache、写前 diff、控制环 LIST 永不打 etcd。实测空载虚拟节点仅 0.2 req/s 且零 LIST。根因很硬：K8s APF 按资源总对象数给 LIST 定价，2500 个 Pod 时一次小 LIST 就能吃满一个优先级层级——限 QPS 没用，只能消灭 LIST。

L1 · Claim 是所有权转移

热池里的沙盒已经调度完、镜像拉完、开机了，SandboxClaim 要做的只是把一台预热好的 Sandbox 的所有权转交出去——语义和 PersistentVolumeClaim → PersistentVolume 的 Bound 一模一样，不需要再过调度器和 kubelet。这层由上游 controller 实现。

L3 · 聚合 APIServer

本栈自研核心：一个 APIService 影子掉 Sandbox CRD，List/Get/Watch 从各节点 NodeInventory 扇出合成，Create/Delete 变成节点本地 RPC。kubectl get sandboxes、RBAC、field selector 照常工作，用户看不见存储已被去中心化。

04

引擎层 cocoon：双 hypervisor 与快照原语

cocoon 是整套栈里年龄最大、协议最宽松（MIT）、也最能单独拿出来用的一层。它把 Cloud Hypervisor 的裸 API 包装成 Docker 式体验，并补齐了上层热池赖以存在的快照克隆语义。

⚙️ 双后端：一份 CLI，两种取舍 Fact

Cloud Hypervisor（默认）Firecracker（--fc）
启动 / 开销~200–500ms · ~10–20 MiB/VM~125ms · <5 MiB/VM
镜像OCI 直启 + cloudimg（UEFI）+ Windows仅 OCI
能力qcow2、多队列网络、热插盘/NIC、VFIO、vhost-user-fs、hugepages几乎全无；--pci 才给有限热插（上限 8 设备）

Analysis默认选 CH 不是因为它快，而是因为只有 CH 能承载完整桌面与 Windows guest；FC 是给「极致密度、无头代码沙盒」留的降级档。sandbox 层的 roadmap 里专门有一条「per-pool hypervisor 轴（ch | fc）」——现在池子按 (template, net, size) 分键，还不能同节点混跑两种引擎，正说明这个双后端还没完全长进上层。

💿 镜像：VM 镜像，不是容器镜像 Fact

cocoon image pull ghcr.io/cocoonstack/cocoon/ubuntu:24.04 拉的是带 kernel + initramfs + rootfs 的 VM 镜像：OCI 层转 EROFS、内容寻址 SHA-256 去重；没有内核的普通容器镜像直接拒绝。cloud 镜像走 URL 拉取自动转 qcow2 v3 + UEFI。官方目录含 Ubuntu 22.04/24.04（及 24.04-xfce、24.04-chrome 变体）、Debian 13、Android 14/15/16、Windows 11，均内置 vsock exec agent。

📸 快照与克隆：上层一切速度的来源 Fact

快照捕获 内存 + COW 磁盘 + 设备状态全量。恢复三模式：mmap（默认，CoW 映射、兄弟克隆共享 page cache、零 eager 拷贝）/ copy（hugepages 等场景回退）/ ondemand（userfaultfd 按需分页）。另有原子 hibernate（存盘失败则 VM 直接 resume）、多轮增量 live migration（靠 XFS reflink 比对 extent）、带稀疏洞保真的 export/import。

硬约束CPU / 内存 / 存储在快照时定死，clone/restore 不接受改规格；要不同形状只能新建 VM。热池按 size 分档就是被这条约束逼出来的。

🌐 网络与资源：密度优化做到 cgroup 粒度 Fact

  • CNI + TC redirect：virtio-net 多队列 TAP 经 TC ingress mirred 接到 CNI veth，数据路径上没有 bridge；MAC 透传以过 Cilium/Calico anti-spoofing，MTU 自动同步；另有 bridge 直连模式与 NIC 热扩缩。
  • 每 VM 一个 cgroup v2 scope：Guaranteed-at-N 默认、cpuset 可钉到一个 cache domain、磁盘队列线程也钉在最闲的域里。
  • 内存回收组合拳：virtio-balloon 默认回收 25%、可选 KSM MADV_MERGEABLE 跨 VM 去重、hugepages 可选（但会失去 mmap 恢复快路径）。
  • 元数据引擎换代：默认 sqlite（旧 json 根目录可离线双向转换）。官方 PR 实测写入比 json 快 30x（N=1）至 11x（N=1000），万级 VM 时读延迟保持平坦——热池规模上去后，元数据层先于 hypervisor 成为瓶颈，他们先修了这里。

Analysis还有一个架构细节值得记：daemon-optional。一台 VM 一个 hypervisor 进程，每条 CLI 命令独立执行；可选的 cocoon daemon 只做崩溃收敛与状态跟踪。这让上层 sandboxd 能直接把 cocoon 当原语调用，不必再和一层常驻 daemon 抢状态所有权。

05

节点层 sandbox：sandboxd 热池与 silkd

sandbox 仓解决的是单节点问题：怎样让「领一台沙盒」这件事快到亚毫秒，池子空了又怎样在几十毫秒内补出来。

图 2 · 节点层数据面。控制面（claim）与数据面（exec/files）在 sandboxd 分开：前者是本地事务，后者是 vsock 中继。

🏊 热池三级火箭 Fact

档位路径延迟
热命中池中已有开机完成的 VM，转交所有权0.2–0.7 ms
池 miss从 golden 快照 mmap 克隆一台几十 ms
冷启从镜像完整开机（裸金属）0.2–0.4 s

池子按 (template, net, size) 分键预热；交付前有一道 warmup 探活 gate——VM 的 envd（及代码解释器）没答活之前绝不交出去，上层曾因此吃过「首个 runCode 返回 502」的亏，现在写进配置契约。

🪼 silkd 与协议纪律 Fact

guest 内产品守护进程 silkd 用 Rust 写，走 vsock 2048 端口的 newline-JSON 帧协议，提供 exec、文件、tar、pty、持久会话、git 操作、后台进程、fork、hibernate、checkpoint、LSP broker 等完整面。线协议有共享的 golden fixture 语料库，Rust / Go / Python 三端测试全部 round-trip 同一份语料——协议漂移直接让 CI 变红。这种「用夹具锁协议」的做法在同类项目里少见。

SDK 侧 Go 与 Python 对等（Python 版纯 stdlib、零依赖），外加 MCP stdio server、OpenAI Agents SDK 与 LangChain 的 provider 适配。

Analysisgossip 是节点层的隐藏关键。各节点的 sandboxd 用 memberlist 互相广播热池水位（亚秒级新鲜），远比上层 NodeInventory 的 5–30 秒发布周期新。于是出现一个双时间尺度设计：控制面用慢而稳的 inventory 做全局视图与选点兜底，节点间用快而局部的 gossip 做 claim 时的最后一跳纠偏——上层 claim 选错节点时，sandboxd 直接回一个指向真有货节点的重定向，而不是失败重试。
06

控制面 sandbox-operator：聚合 APIServer

名字叫 operator，实际上它不跑传统 controller reconcile——它自己声明「ships no controller of its own」。核心是三个二进制与一个 CRD。

🧩 组件清单 Fact

组件职责
cmd/sandbox-apiserver聚合 APIServer：scatter-gather 读、节点本地 claim/release、pause/resume/fork/snapshot 子资源、可选 e2b REST 面、进程内 WarmPool 驱动
cmd/sandbox-envd-proxye2b 数据面：单一公网入口，按 claim 把 files/commands/pty 经 vsock 送进正确的 guest，客户端永远看不到节点地址
cmd/sandbox-e2b无 K8s 形态：同一 e2b 面直接跑在 sandboxd mesh 上，靠 gossip 发现节点，可同进程内嵌 envd-proxy
NodeInventory CRD本仓唯一自有 CRD（独立 API 组 sandbox.cocoonstack.io）：每节点一份的实时摘要——在册沙盒、热池容量、已晋升模板、sandboxd 地址

安装形态有个关键取舍：Helm chart 装的是一个会影子掉上游 Sandbox CRD 的 APIService——L3 集群因此不装上游 Sandbox CRD、不跑上游 controller。想要 Pod 路径就装上游的整套清单。两条路径最终都落到同一个 sandboxd 热池，区别只在 K8s 里存什么。

🎯 选点：power-of-two-choices Fact

NodeInventory 每 5–30 秒才发布一次，若每次 claim 都挑「快照里最热的节点」，一个发布窗口内的突发流量会把那台节点抽干、其它节点闲置——它自己的 100 连发实测里 2 次 miss 正是单节点过载的冷启。解法：从有热容量的候选里随机抽两个，取更热的那个。偏向热容量与摊匀突发兼得。若快照仍选错，sandboxd 的 gossip 重定向补最后一跳（双机实测一跳 0.57ms）。

⏳ 一致性账本：哪些是强的，哪些是最终一致的 Fact

  • List / Watch：最终一致，随 inventory 发布周期（~30s）收敛；watch 目前靠轮询 inventory 做 diff 实现。
  • Get 与生命周期操作：按名字或 claim id 直查节点，在任意副本上立即准确——专门补读己之写。
  • Create 不是 upsert：同名重复 Create 会再 claim 一台新 VM，可靠调用方应使用 generateName，以响应里的 claim-id 锚定身份。
  • 节点死亡：其 inventory 超过 90 秒未更新即退出 claim 路径、其沙盒从读视图消失并发出 Deleted 事件；节点本身还活着时 sandboxd 仍在本地履约租约。
注意WarmPool 驱动与 apiserver 同进程。它 watch SandboxWarmPool、把模板解析成 (template, net, size) 键、把期望副本数摊到各节点、再把 status.readyReplicas 按节点上报写回。reconcile 是 O(pools + nodes)/tick，永不 per-sandbox——这是「apiserver 后台负载不随沙盒数增长」的结构性原因，也是它敢宣称 100 万意图的底气。但代价写在 roadmap 里：多副本 HA 未完成，今天多副本只分担读，claim 偏向单写者。
07

性能账本：50,000 台 / 15 秒的出处

这一节把官方 performance.md 的数字逐条溯源：方法、硬件、轮次、反例。它是本报告最看重的一节——不是因为数字大，而是因为记账方式少见地诚实。

🚀 舰队供给：一次 patch 拉满 5 万台 Fact

方法：单个 SandboxWarmPool 把 replicas: 0 → 50000，跑在 20 台同构裸金属（每台 384 vCPU / 1.5 TiB / 本地 NVMe，每节点 2,500 台 microVM）。status.readyReplicas 以 1 秒粒度轮询，节点侧遥测以 5 秒粒度交叉核对。沙盒是真实 Cloud Hypervisor/KVM microVM，从 golden 快照恢复。

结果：全量供给 10–15 秒（节点遥测）/ 15.7 秒（CR 墙钟），有效速率 3,300–5,000 台/秒；每台净内存 99 MB；全程 etcd 约 2 写/秒（20 份 inventory 每 30 秒发布 + 少量 status），且 claim 路径对 etcd 零写入。

轮次节点恢复路径填满耗时
126eager copy（全量拷贝）172.7 s
226（含 1 台 HDD 节点）mmap CoW290.1 s
320（同构 NVMe）mmap CoW12 ± 3 s

反例不藏第 2 轮是官方自曝的负优化：同一轮里每台 NVMe 节点都变快了，唯独那台 HDD 节点让 mmap CoW 从约 140 秒退化到约 295 秒——优化的符号由存储介质决定。去掉 6 台异构节点才得到第 3 轮的干净曲线。把反例写进自家性能文档，这一笔比 5 万这个数字本身更值钱。

🧮 内存账本：99 MB 是怎么算出来的 Fact

恢复方式CH RSS私有共享净 / VM
eager copy359 MB3536358 MB
mmap CoW163 MB966799 MB

口径来自 /proc/<pid>/smaps 与节点 MemAvailable 差值互证。扩展律写作 T(S,N) ≈ T₀ + S/(N·r)，其中节点本地常数 r ≈ 200–270/s、控制面常数 T₀ ≈ 5–6s。r 恒定的原因是供给所需的一切（golden 镜像、256 路 refill 预算、SQLite 元数据）全是节点本地的，控制面对每节点只有每 5 秒一次 O(1) 的 PUT /v1/pools——节点间零耦合，于是集群速率 = N·r。外推表给到 200 节点 / 100 万台约 25 秒，并明确标注为外推而非实测（roadmap 里「百万级验证」仍在长期清单）。

⚡ Claim 延迟：分两层看 Fact

  • 节点本地：sandboxd 所有权转移 0.2–0.7 ms。
  • 经 K8s API 全链路：26 节点舰队（每节点 125 台热池）上 create → Ready p50 < 1s，p95/p99/max 均为 1s；100 个 Sandbox CR 提交耗时 2.9s，98/100 热命中，2 次 miss 是单节点过载的冷启而非控制面问题；突发下 APF 队列深度全程为 0。
  • 上游 controller A/B（2026-09-22，双机各 30 热池）：上游 v1.0.3 claim p50 48–54ms，与被删的自维护 fork（44–52ms）落在同一噪声带内——官方据此判定可以放心交还上游。池被抽干后的突发场景里，瓶颈被定位在 virtual-kubelet 默认每节点 10 次/秒的 Pod 同步限速，放开到客户端预算后 refill 达 103–104/s。
  • 每 claim 的 etcd 成本（Pod 路径）：21–24 次 apiserver 写、18–21 次 etcd put；关掉三项可选事件/标注后降约 19–23%。而 L3 路径这一项是 0——这正是两条路径的本质差价。
Analysis怎么读这份账本：供给速率（万台/十几秒）测的是「热池预热」而非「用户请求延迟」，两者别混；claim 的亚毫秒是节点本地数字，全链路 p50 <1s 才是应用视角。官方把三者分开记账、把 retired 的 fork 数据单独归档并注明「描述的是已不在仓里的代码」，是这套数字可被引用的前提。本报告所有性能结论均标注为厂商自测（Fact 层为「官方如此宣称且方法可复现」），尚无第三方复测——见 §14。
08

生命周期与 e2b 兼容层

上游 agent-sandbox 的 API 只有 create/delete 级别语义。CocoonStack 在 L3 上补了四个动词，并把同一套语义翻译给 e2b SDK。

🔀 四个子资源动词（L3 独有） Fact

子资源效果
sandboxes/pause快照 guest 内存并停机（成本与内存大小成正比）
sandboxes/resume走 cocoon mmap 快路径恢复（实测 109ms vs pause 315ms）
sandboxes/fork同节点克隆 N 个子沙盒，源继续运行；子沙盒各自独立租约，不继承父租约
sandboxes/snapshot打 checkpoint，供后续沙盒从它分支

这些动词以子资源形式挂在上游 agents.x-k8s.io/v1beta1 组下，标准 Sandbox schema 不动，未修改的上游客户端照常工作。四个动词全线拒绝 server-side dry-run——节点 API 没有 dry-run 事务，装不出来就明说。

🔌 e2b 兼容：平移层，不是第二控制面 Fact

export E2B_API_URL=http://your-apiserver:8080
export E2B_API_KEY=<key>
# 未修改的 e2b SDK：
# Sandbox.create('ghcr.io/.../rt:24.04') 直接 claim 热池
# 同一台沙盒同时出现在 kubectl get sandboxes 里

映射覆盖 create/list/get/delete、timeout/refresh（续租）、pause/connect（恢复）、fork、snapshot，以及模板 build API（并行度、超时、日志行数、构建产物走本地目录或 S3）。模板别名文件把 e2b 的 base / code-interpreter-v1 映射到本栈镜像。启动期强校验：没配 API key 文件又没显式允许匿名、没配 --e2b-domain、没配 envd 密钥文件，任一缺失直接启动失败——不给「裸奔的 claim 端点」留静默缺口。

快照的持久性边界checkpoint 只活在打出它的那台节点上。节点磁盘丢了，checkpoint 就没了；对等节点能搬运记录但够不到数据本身，官方明确不做复制，理由写在 roadmap 里：「checkpoint 是 agent 工作负载的分支点，不是备份」，复制的写放大不值得。需要跨节点存活的状态，正道是 promote 成模板再分发。把这条边界当设计前提接受，CocoonStack 的 fork/snapshot 语义才是自洽的；拿它当持久化存储用，会丢东西。
09

协议边界：MIT 与 AGPL 的分界线

这是整套栈最容易被忽略、但对商用接入决定性的一节。三层协议不一致，分界线画得非常具体。

部件协议说明
cocoon 引擎（含 vk-cocoon、cocoon-operator 等早期周边）MIT可自由嵌入、修改、商用，无 copyleft 传染
sandbox 服务端：sandboxd、silkd、boot 链、OS 镜像、MCP serverAGPL-3.0官方原话：这一层「is a product」
sandbox 客户端：Go/Python SDK、OpenAI/LangChain 适配、wire 协议模块Apache-2.0各目录自带 LICENSE，明确无 copyleft 义务
sandbox-operator 全部自有代码AGPL-3.0其消费的上游 agent-sandbox API 类型是 Apache-2.0 依赖，未复制源码入仓
vk-sandboxAGPL-3.0与较早的 vk-cocoon（MIT）不同——同一组织内新旧部件协议不同，接入前逐仓核对

Analysis分界线的意图很清楚：引擎开源引流，产品层用 AGPL 守住托管生意——你可以拿 cocoon 去搭自己的栈，但如果你把 sandboxd / sandbox-operator 改一改就对外提供网络服务，AGPL 的源码提供义务会被触发。对接入方的实操结论：只取引擎层（MIT）+ 自写控制面，是法律上最干净的切法；整套托管商用，先过法务。这一点与 E2B（托管服务、引擎闭源）、OpenSandbox（Apache-2.0 全开放）的站位都不同，选型表里必须单列。

10

安全模型：隔离在 VM，战场在网络

官方 security.md 只写了一页，但边界划得干净。结合本档案馆的一贯结论看：microVM 逃逸面与网络出口面要分开评估。

🧱 信任边界 Fact

  • K8s 面：标准 authn/authz + RBAC 管 agents.x-k8s.io 资源；e2b 面用独立 API key 文件，按 key 绑定 namespace 隔离。
  • Claim 令牌：节点 claim 用 sandboxd bearer token；每台沙盒交付时发 per-claim token（K8s 面是 annotation，e2b 面是其 HMAC 派生的 envdAccessToken）。泄漏一张只失守一台沙盒、且只到它的数据面，不及宿主机。
  • envd-proxy 是高价值目标：它同时持有全舰队 sandboxd token 与 envd 密钥，校验来访 token 的派生关系后才用 claim token 开中继——客户端永远学不到节点地址，但这也意味着 proxy 本身是全舰队的钥匙串，其部署边界需按控制面等级保护。
  • 隔离原语：硬件虚拟化 microVM；guest 逃逸被定义为下层 hypervisor 栈的漏洞，走 GitHub 私密 Security Advisory 上报，不开公开 issue。

🌐 网络默认硬化 Fact

  • net=none 为默认车道：guest 没有网卡，全部 I/O 走 vsock 经 sandboxd 中继——无网 guest 也能 exec/传文件，但没有任何直接出口。
  • net=egress 需显式选择：挂 CNI/bridge 网卡；e2b 面上 allow_internet_access: true 才映射到 egress，其余一律 none。模板 build 沙盒恒走 none，只能经 sandboxd 的 guarded egress proxy 出网。
  • 带签名的文件 URL（envd 49983 端口）是唯一免 token 放行的请求：proxy 用舰队 token 中继且保持被动（不唤醒暂停的沙盒），签名由 envd 自行校验。

Analysis与本档案馆此前对 SPACE 的取证结论互证：VM 隔离层很难被打穿，真实世界的失守多发生在 egress。CocoonStack 把默认车道设成「根本没网卡」而不是「有网卡再加防火墙规则」，是把攻击面从策略问题降维成拓扑问题——规则会写错，物理不存在的网卡不会。

已知问题与风险：fork 依赖与未竟之路

cocoon 的 known-issues 文档长达 444 行。文档诚实是优点，但每一条都是接入方要替它还的债。

⚠️ 风险清单 Fact Analysis

风险具体形态等级
三个 dev fork 承重Cloud Hypervisor 必须 v54+ 且用 cocoonstack fork 的 dev 滚动构建（diff 快照、shadow-stack 保存恢复、QCOW 泄漏修复）；Firecracker 必须 1.16.1+ fork 版（1.16.0 恢复后永久损坏 vsock）；x86 固件必须 fork 的 dev 版（上游 0.5.0 连 Windows ACPI 关机都做不对）。cocoon-check --upgrade 装的全是这些滚动构建高——生产稳定性押在三个滚动 dev 分支上，上游漂移即是自己的故障

控制面未竟项（官方 roadmap）聚合 apiserver 多副本 HA 未完成（读可分担、claim 偏单写）；watch 仍是轮询 diff 而非 per-node 流合并；L2 节点本地 claim 网关只有设计；per-pool hypervisor 轴未落地；百万级全栈验证未做中——当下规模可用，往 10 万+ 台走前需逐项验收

13

对 Cassia 的启示：可拿走与不可拿走

站在 Cassia（AI agent 操作系统：真实电脑 + 实时可见操作 + 持久环境）的立场做一次能力审计。本节为本档案馆的分析立场，非官方结论。

✅ 可直接拿走的四样 Analysis

  1. NodeInventory scatter-gather 模型：Cassia 若走向多节点自托管，这是避免重蹈「每沙盒一个对象」覆辙的现成设计，连失败模式表（节点分区、inventory 丢失、控制面停写）都替你枚举好了。
  2. 热池交付纪律：(template, net, size) 分键 + warmup 探活 gate（envd 没答活绝不交付）。Cassia 在 E2B 上吃过的「沙盒领到但环境没就绪」类问题，这套纪律是结构化解法。
  3. fork / pause 语义设计：子沙盒独立租约不继承父租约、snapshot 命名空间戳、pause 成本与内存成正比的诚实标注——做分支型 agent 工作流时可直接参照。
  4. power-of-two-choices 选点：任何「从慢更新的全局视图里挑节点」的场景都适用，比最优选择更抗突发。

🚫 拿不走 / 要付代价的三样 Analysis

  1. 整套托管商用先过 AGPL：产品层（sandboxd/operator）是 AGPL-3.0，与 Cassia 现行 MIT 发布策略不兼容。干净的切法是只取 cocoon 引擎（MIT）+ 自写控制面，而非整栈搬运。
  2. 运维形态不匹配：它要求裸金属 KVM 舰队与三个 fork 的滚动构建；Cassia 当前部署（单机 + E2B）没有这个运维面，接进来等于新开一条 infra 战线。
  3. 叙事不重合：CocoonStack 的主线是无头代码沙盒舰队，桌面只是 cocoon 的一个镜像变体；Cassia 的差异化在「真实电脑 + 实时可见 + 持久环境」。可借的是它的引擎与快照原语去承载桌面镜像，不是它的控制面叙事。
审计结论：对 Cassia，CocoonStack 的正确打开方式是当参考架构与原语库读，不当平替平台迁。近期动作建议只有一条：保持 P0 级 release 跟踪（cocoon 的版本节奏最快、且 MIT 层变化直接决定可复用边界）；真要验证供给速度，需借一台 KVM 裸金属做单节点 sandboxd 三数基准（热 claim / golden 克隆 / pause-resume），普通云主机与嵌套虚拟化环境测不了，也不该拿测不了的环境数据下结论。
